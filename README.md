# ПБЛ Павлодар — сайт баскетбольной лиги

Сайт Павлодарской баскетбольной лиги на Next.js 16 (App Router, React 19, Tailwind 4).

**Данные.** Команды, тренеры, заявочные составы и матчи стартового тура — официальные:
9 команд и 122 игрока дивизиона A, сезон 2026/27, открытие 1 ноября 2026 года.
Счёт и статистика сыгранных матчей до этой даты генерируются детерминированно,
чтобы таблица, лидеры и протоколы были наполнены до начала настоящего сезона.
Пользовательские данные (протоколы столика, аккаунты, заявки) хранятся в `localStorage`.

## Запуск

```bash
npm run dev     # http://localhost:3000
npm run build
npm start
npm run lint
```

> **Запускать только внутри WSL.** `node_modules` собран под Linux, поэтому запуск сборки
> из Windows падает на нативном бинарнике `lightningcss.win32-x64-msvc.node`. Если команда
> вызывается снаружи:

> ```bash
> wsl -d Ubuntu -- bash -lc 'cd ~/Projects/pbl-basket-mvp && npm run build'
> ```

## Живой протокол (play-by-play)

`lib/live-feed.ts` — единая лента событий матча. Источник истины — `localStorage`
(ключ `pbl.live.<matchId>`): запись синхронная, интерфейс обновляется мгновенно и работает
без сети. Supabase подключается поверх и не является обязательным:

* `appendEvent()` пишет локально и **фоном** отправляет строку в таблицу `live_events`
  (ошибка сети только логируется — UI не падает);
* `useLiveFeed(matchId)` читает локальный кэш и, если клиент сконфигурирован, держит
  realtime-подписку; входящие события сливаются в тот же кэш через `mergeEvent()`,
  поэтому путь отрисовки общий;
* `truncateEvents()` обслуживает кнопку «Отменить» в судейском столике.

Каждое событие несёт таймкод (`период` + `MM:SS`), сторону (`home` / `away` / `system`),
тип (`score`, `miss`, `foul`, `timeout`, `stat`, `period`, `system`), очки и игрока.
Компонент `components/PlayByPlay.tsx` разделяет команды цветом (левая рамка и подпись
берут цвет клуба), подсвечивает тип события плашкой и умеет фильтровать ленту по командам
и только по очкам. Лента используется в `/scorer`, `/stream/[id]` и на странице матча.

## Supabase

```bash
cp .env.example .env.local
# NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
# NEXT_PUBLIC_SUPABASE_ANON_KEY=<publishable key>
```

Клиент (`lib/supabase.ts`) опционален: без переменных `isSupabaseConfigured === false`,
`getSupabase()` возвращает `null`, и приложение полностью работает офлайн.
Переменные читаются статически (`process.env.NEXT_PUBLIC_*`), поэтому **после правки
`.env.local` dev-сервер нужно перезапустить**.

Используются две таблицы:

| Таблица | Назначение |
| --- | --- |
| `applications` | Заявки команд из формы `/request`: `team_name`, `captain_name`, `phone`, `email`, `division`, `roster`, `comment` |
| `live_events` | Лента событий матча (`supabase/schema.sql`) |

`lib/applications.ts` пишет заявку в `applications`; локальная копия в `localStorage`
нужна только для блока «Мои заявки» в этом браузере. Читать чужие заявки с клиента
нельзя — там персональные данные, поэтому список всех заявок на сайте не выводится.

## Черновики: состояние переживает F5

Судейский столик и форма заявки сохраняют ввод в localStorage, чтобы случайная
перезагрузка не стоила судье счёта, фолов и таймера.

| Ключ | Что хранит | Когда очищается |
| --- | --- | --- |
| `statix_active_match_session` | настройки матча + счёт, фолы, тайм-ауты, четверть, таймер, пятёрки на площадке, история отмены | «Завершить и сохранить» — удаляется; «Новый матч» — остаётся только настройка |
| `statix_draft_team_request` | черновик формы заявки | после отправки и по кнопке «Очистить» |

Три детали реализации:

1. **Запись мимо `notify()`.** `lib/match-session.ts` и `lib/form-draft.ts` пишут
   в localStorage напрямую: во время игры состояние меняется раз в секунду, и будить
   всех подписчиков client-store на каждый тик было бы дорого. Черновик весит ~5 КБ,
   запись занимает ~0.02 мс.
2. **Восстановление без ошибки гидратации.** Черновик читается через
   `useClientStore`, то есть до конца гидратации отдаётся `null` и разметка совпадает
   с серверной. Затем столик перемонтируется с `key`, завязанным на `useHydrated()`,
   и все значения подставляются прямо в инициализаторы `useState` — без синхронизации
   через эффект. Автосохранение заблокировано флагом `canPersist`, иначе первый
   рендер успел бы затереть восстановленный матч пустым состоянием.
3. **Часы после перезагрузки стоят.** `running` намеренно не восстанавливается:
   когда продолжать отсчёт, решает судья. Столик показывает об этом уведомление.

Повреждённый или чужой по версии черновик игнорируется — столик открывается
с экрана настройки, а не падает.

## Клиентское состояние и гидратация

Next 16 включает правило `react-hooks/set-state-in-effect`, а Cache Components запрещают
`new Date()` при пререндере. Поэтому клиентские значения (localStorage, сегодняшняя дата)
читаются через `useSyncExternalStore` с кэшированным снимком — `lib/client-store.tsx`.

Важная особенность, которую пришлось учесть: **на `getServerSnapshot` полагаться нельзя**.
React вызывает его при серверном рендере, но при гидратации успевает перерисовать поддерево
уже клиентским снимком, и разметка расходится — проверено на теме, состоянии входа и
избранном. Поэтому:

1. `HydrationGate` держит флаг «гидратация завершена»; до его поднятия `useClientStore`
   возвращает серверное значение, и разметка гарантированно совпадает.
2. Флаг работает, только если гейт и его потребители гидратируются в одном проходе.
   Из-за этого в `app/layout.tsx` **нет общих границ `<Suspense>`**: шапка внутри такой
   границы гидратировалась позже провайдеров и получала клиентские значения слишком рано.
   Свои границы есть у `components/NavLinks.tsx` (единственное место с `usePathname()`)
   и у страниц, читающих параметры адреса.
3. Тему переключатель рисует вообще без участия React-состояния: обе иконки всегда в
   разметке, нужную показывает CSS по `data-theme`, который инлайн-скрипт ставит до первой
   отрисовки. То же — для выбора темы в настройках.

При добавлении новой разметки, зависящей от localStorage, помните: она не должна отличаться
от серверной до завершения гидратации.

## Данные

`lib/league-data.ts` содержит реальные справочники лиги (`TEAMS`, `ROSTERS`, `REAL_FIXTURES`)
и разворачивает их в двухкруговой календарь сезона с бокс-скорами. Генератор детерминированный
(`mulberry32` + FNV-хэш), поэтому сервер и клиент всегда получают одинаковые цифры.
Матчи до `SEASON_OPENING` считаются сыгранными, матчи стартового тура — настоящие и
показаны как предстоящие. Эмблемы команд лежат в `public/teams/<team_id>.webp`.

Файл сгенерирован из официальной выгрузки лиги; при обновлении составов его нужно
перегенерировать, а не править вручную.
